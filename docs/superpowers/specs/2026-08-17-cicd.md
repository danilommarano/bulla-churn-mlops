# CI/CD com GitHub Actions + Jenkinsfile — Design (Marco 7)

> Entregável do teste técnico Bulla (ML Engineer / MLOps). Espelha localmente o
> **Cloud Build / Cloud Deploy** do Vertex AI com equivalentes open-source, sem cloud.

## 1. Objetivo

Adicionar CI/CD ao pipeline de churn: em cada PR/merge, validar qualidade de código,
rodar a suíte de testes, exercitar a pipeline de treino (KFP) com o quality gate e,
no merge para `main`, publicar a imagem da API num registry. Cobre a peça que faltava
do ciclo de vida MLOps: **automação de integração e entrega**.

Restrições: roda **localmente/no CI hospedado do GitHub, sem GCP**. O Jenkinsfile é
documental (não há servidor Jenkins) — respeita o constraint local/no-cloud do teste.

## 2. Mapeamento Vertex AI ↔ OSS (com gaps honestos)

| Vertex AI / GCP | Equivalente neste repo | Gap honesto |
|---|---|---|
| Cloud Build + build triggers | **GitHub Actions** (`.github/workflows/ci.yml`) — executa de verdade | Sem worker pools privados / VPC |
| CI enterprise self-managed | **Jenkinsfile** declarativo (documentado, não executado) | Sem servidor/agente Jenkins ativo |
| Artifact Registry | **GHCR** (`ghcr.io/danilommarano/churn-api`) | Registry do GitHub, não do GCP |
| Vertex Pipelines / Continuous Training | **DAG KFP** rodado no CI (`make pipeline`) | Roda no runner, não em cluster gerenciado |
| Vertex model validation | **quality gate** `roc_auc >= min_roc_auc` (já em `register_model`) | Gate reusado do Marco 5, não novo |
| Cloud Deploy → endpoint gerenciado | push da imagem ao GHCR (deploy fica manual/local via `docker run`) | Sem deploy automático a endpoint rodando |

## 3. Arquitetura

Três artefatos + um aditivo no Makefile. Princípio: **DRY** — o Makefile é a fonte
única dos passos; Actions e Jenkins só chamam `make <target>`.

- `Makefile` — adiciona `format-check` e `ci` (reutilizados por todos).
- `.github/workflows/ci.yml` — o CI/CD que roda de verdade.
- `Jenkinsfile` — o espelho declarativo documentado.

### 3.1 Makefile (aditivo)

```make
format-check: ## Checa formatação sem alterar (usado no CI)
	uv run ruff format --check src tests

ci: ## Roda a sequência de CI localmente (espelha o GitHub Actions)
	$(MAKE) lint
	$(MAKE) format-check
	$(MAKE) test
	$(MAKE) docker-build
	$(MAKE) pipeline
```

`.PHONY` ganha `format-check ci`. `make ci` serve pra reproduzir o CI localmente e
como documentação executável da sequência.

### 3.2 GitHub Actions — `.github/workflows/ci.yml`

Um único workflow, jobs paralelos, `publish` gated no merge para `main`.

**Gatilhos:** `pull_request` (qualquer branch) e `push` em `main`.

**Jobs:**

1. **`lint-test`** — setup-uv (Python 3.12, cache habilitado) → `uv sync` →
   `make lint` → `make format-check` → `make test`. Cobre os 76 testes.
2. **`ml-pipeline`** — setup-uv → `uv sync` → `make pipeline`. Roda o DAG KFP
   ponta a ponta (`prepare → split → train → evaluate → register`), exercitando o
   quality gate `roc_auc >= min_roc_auc`. É o leg de **Continuous Training**: prova
   que a pipeline de treino continua íntegra a cada mudança. Depende do CSV
   versionado (`Customer-Churn-Records.csv`, já no repo).
3. **`docker-build`** — `if: github.event_name == 'pull_request'` → `make docker-build`.
   Valida que a imagem builda, sem publicar. Só em PR (no merge, `publish` já builda).
4. **`publish`** — `needs: [lint-test, ml-pipeline]`,
   `if: github.event_name == 'push' && github.ref == 'refs/heads/main'`,
   `permissions: packages: write` → `docker/login-action` no GHCR com `GITHUB_TOKEN`
   → `docker/build-push-action` com tags `:latest` e `:${{ github.sha }}`. Leg
   **CD → registry** (Artifact Registry). Sem duplicar build: `docker-build` só roda
   em PR, `publish` só na `main`.

**Ambiente:** `ubuntu-latest`; `astral-sh/setup-uv@v6` (cache do uv por padrão);
`actions/checkout@v5`; `docker/login-action@v3` + `docker/build-push-action@v6`.
Sem secrets manuais — `GITHUB_TOKEN` já autentica no GHCR do próprio owner.

### 3.3 Por que `publish` depende do `ml-pipeline`

A imagem só é publicada se a pipeline de treino **e** os testes passarem. É o análogo
do gate do Vertex: não promove/entrega um build cujo modelo não valida. Não há push a
registry a partir de código quebrado ou de um modelo abaixo do threshold.

### 3.4 Jenkinsfile (raiz)

Declarative pipeline com cabeçalho comentado explicando: (a) que é o equivalente
Cloud Build enterprise, (b) que **não é executado** aqui (sem servidor Jenkins), (c)
que rodaria num agente real com `uv` + `docker`. Stages espelham os targets:

```groovy
// Equivalente enterprise self-managed do Cloud Build (Vertex AI CI/CD).
// Documental: não há servidor Jenkins neste teste (constraint local/no-cloud).
// Rodaria num agente com uv + docker disponíveis, reusando os mesmos make targets
// que o GitHub Actions — fonte única de verdade dos passos (DRY).
pipeline {
    agent any
    stages {
        stage('Setup')    { steps { sh 'uv sync' } }
        stage('Lint')     { steps { sh 'make lint' } }
        stage('Format')   { steps { sh 'make format-check' } }
        stage('Test')     { steps { sh 'make test' } }
        stage('Build')    { steps { sh 'make docker-build' } }
        stage('Pipeline') { steps { sh 'make pipeline' } }
    }
}
```

## 4. Verificação (honesta)

CI é configuração, não código testável por pytest — **não há testes unitários de YAML**.
A prova é operacional, em três camadas:

1. **Lint estático do workflow** — `actionlint` (ou `yamllint`) local no `ci.yml`.
2. **`make ci` verde localmente** — roda lint + format-check + test + docker-build +
   pipeline na máquina, provando que os passos que o CI executa funcionam.
3. **Run real do GitHub Actions verde** — após abrir o PR, confirmar que o workflow
   roda e fica verde de verdade no GitHub. Num entregável avaliado, esta é a prova que
   conta. O `publish` só é observável no merge para `main` (é aceitável validar o job
   por inspeção + o run de PR dos demais jobs).

**Ponto a verificar no plano:** se o quality gate reprovar (`roc_auc < min_roc_auc`),
o `make pipeline` deve **sair com código ≠ 0** pra o job `ml-pipeline` falhar. Se hoje
o `register_model` só pula a promoção sem levantar erro, o plano adiciona a asserção
mínima pra o CI capturar um modelo ruim (falhar o build).

## 5. Fora de escopo (YAGNI)

- Servidor/execução real de Jenkins (só o Jenkinsfile documental).
- Deploy automático a um endpoint rodando (serving continua local via `docker run`).
- Matrix multi-versão de Python (fixo em 3.12, o `requires-python` do projeto).
- Cron de retraining agendado (o equivalente Vertex Pipelines schedule; o monitoramento
  do Marco 6 já é on-demand).
- Badge de status no README (fica pro Marco 9, junto do README final).
- Cache/otimização além do cache padrão do `setup-uv`.
